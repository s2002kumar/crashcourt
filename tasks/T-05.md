## Decisions
1. **The delayed ack uses a long `latency` toxic.**
   - Measured and confirmed in Toxiproxy's source: a `timeout` toxic with timeout=0 drops data ("Drop the data on the
     ground"), and removing it closes the connection. Spec section 10 assumed it holds responses for release.
   - So `drop_responses` (the `timeout` drop) is the lost ack (F11). `hold_responses` (a 24-hour downstream latency) is
     the deterministic delayed ack (F12): removing it forwards the held data.
   - Details: research/fault-selftest.md. I flagged this on the issue because it corrects a statement in the spec.
2. **Holds must be alone.** A new toxic on the held stream releases a latency hold at once; a toxic on the other stream
   does not. `hold_responses` refuses a proxy that has toxics, and the other fault functions refuse to add a toxic while
   a hold is active. The self-test proves both halves.
3. **Bookkeeping.** `fault.inject` is written before the fault is applied. Every inject gets exactly one `fault.heal`:
   when healed, at once for instantaneous faults (kill, termination, restart), or with the error if applying or healing
   failed, which also raises `FaultError` so the trial is INVALID.
4. **Safety.**
   - `ToxiproxyClient` refuses a non-loopback API URL.
   - `ensure_proxy` never replaces an existing proxy, which would drop live connections, and fails if its upstream is
     not the target database.
   - `restart_database` checks the container's `com.docker.compose.project` label.
   - `terminate_backends` needs an explicit application_name and skips its own backend.
5. **Signals need POSIX.** On Windows the signal functions raise, and the self-test reports `skip` for that check. On
   Linux a skip would fail the integration test.
6. **Per-worker targeting is not solved here.** Toxics apply to every connection through a proxy. A worker-specific
   network fault needs one proxy and port per worker, which is for T-07 and T-12 to decide.
