## Decisions
1. **Nodes run inside the harness.** Each node opens `harness.node(name, config)`: it takes its attempt from the
   sink's counter `node/<thread>/<node>/<turn>` (outside the worker, so a re-run or a replacement worker gets the
   next attempt), writes `node.start` with the op, thread, task id, the checkpoint the task runs from, and the
   attempt, and writes `node.end` when the node returns (outcome completed), pauses at `interrupt()` (outcome
   interrupted), or raises (status fail). Effects are posted from inside the node that causes them and carry its
   attempt; the scripted model's answers carry it too. One counter per node execution serves the node, its
   effects, and its model call, so they always agree.
2. **The task id is LangGraph's own.** A node reads `__pregel_task_id` from its configuration: the id LangGraph
   passes to `put_writes` for that task's writes, so the checker can join committed writes to the node that wrote
   them. The checkpoint a task runs from is `checkpoint_map[""]`, which equals the `checkpoint_id` on its
   `put_writes`. Both were confirmed against LangGraph 1.2.12 before use; neither is a public API, so a test checks
   the join (each node's writes, by task path, carry exactly that node's task id; the other writes are the
   `__start__` input task's and the resume value's under the null task id).
3. **W1's effect model**, as the methodology freezes it: approve fires exactly one `charge:<thread>` from execute,
   after the interrupt, with `data.decision` on its request equal to the resume value execute received; reject
   fires none; record writes `decision` and `executed` (each charge's key and attempt). The misuse variant posts
   `precheck:<thread>` from approval before `interrupt()`; LangGraph re-runs the interrupted node on resume, so it
   fires twice per run (attempts 1 and 2), whatever the decision. An effect's `logical_op` is its key. A refused or
   unanswered effect request is recorded (fail or info) and raised: never retried or skipped.
4. **Resumes are first-class ops.** An op with `resume: <value>` is sent as `Command(resume=value)`; an op is a
   resume or carries input, never both. `client.invoke` records the resume value, so the client view shows what
   each resume asked for. The field enters every scenario's hash, so the smoke scenario's pinned hash changed.
   Scenarios may also name a landmark table (`landmarks: <name>`, default none), which the checker resolves to
   scenarios/landmarks/<name>.yaml and verifies every failpoint hit against (the methodology's section 4.2). The
   loader checks only the name's form, so scenarios stay independent of checker files. It enters the hash too,
   since the table is part of what a fault cell runs. T-09's fault-free scenarios name none.
5. **W5** is one node, respond, answering each user turn from the scripted model; a turn's index is the number of
   earlier user messages. Each answer's text and id name the thread, turn, and attempt.
6. **W5 concurrent continues an existing conversation.** w1 answers a first turn; then two new turns go to w1 and
   w2, each parked right after reading the head, and released together. Both continue the same checkpoint, so the
   lineage forks at one parent (and the counter gives their answers attempts 1 and 2 of turn 1, so the two runs are
   distinguishable). On an empty thread the two writers would instead each create a root; the checker's I5a covers
   both shapes, and the first is the "concurrent continuation" the spec names.
7. **Determinism is judged on what the trials left.** research/evidence/t-09/determinism.py compares every trial's
   ledger rows, terminal client events and outputs, and, per thread, the latest checkpoint's saved state and the
   lineage's shape, read directly from Postgres with `LANGGRAPH_STRICT_MSGPACK=true`. Thread prefixes, sequence
   numbers, times, checkpoint ids, and pids are removed first. It reads the database only to report on finished
   batches. W5 concurrent is not expected to be deterministic in its head (which branch commits last is the race
   the barrier sets up); its lineage shape is reported instead.

## Card (issue #18)
Deliverables:
- `workloads/w1_approval.py`: plan, then an approval node that calls `interrupt()`, then execute, which posts one
  effect to the sink, then record. The resume value is approve or reject. Approve fires exactly one effect, reject
  fires none, and the decision saved in state matches (**done**).
- The misuse variant, in the same file: the effect sits before `interrupt()` in the approval node. The node
  restarts from its beginning on resume, so the effect fires once before the pause and again on resume, whatever the
  decision. That duplicate is documented behavior, and it has to show up every time (**done**).
- `workloads/w5_continuation.py`: two new user turns on one thread, one per worker, answered by the scripted model
  (**done**).
- Model responses come from T-08's scripted model, keyed by thread, node, turn, and attempt, with the attempt number
  embedded in every response. Attempt counters stay in the sink (**done**).
- Every effect request carries the fields the sink requires: effect key, logical op, op id, attempt, worker, pid,
  thread, node, the checkpoint id the worker had loaded, a payload hash, and the trial it belongs to (**done**).
- Scenario YAML for W1 approve, W1 reject, W1 misuse, W5 with one worker taking both turns in sequence, and W5 with
  two workers held after `get_tuple` and released together, ready for the checker in T-10 (**done**).
- W1's `effect.request` records `data.decision`: the decision the executing attempt acted on, `approve` or
  `reject`, taken from the resume value it received. T-10's I8 compares it with the RESUME write in the head
  lineage. This is the only acted-on value recorded; there is no generic payload field. It lives in the existing
  free-form `data`, so schema v1 is unchanged (**done**).
- Every `node.start` and `node.end` carries `task_id` (the existing envelope field), the same task id LangGraph
  passes to `put_writes`, so T-10 can join committed task writes to the node that produced them (I2, I4(d), and
  landmark validation) (**done**).

Tests:
- One worker, no faults: the ledger holds exactly one effect for approve and none for reject, and the saved
  decision matches (**done**: unit and integration).
- The misuse variant fires its effect exactly twice per interrupted run, with both attempts recorded (**done**).
- W5 with one worker produces a single chain containing both turns (**done**).
- W5 with two workers and the barrier runs to completion with one terminal client event per request. Detecting and
  classifying the fork is T-10's job (**done**).
- 50 fault-free trials per variant produce the same ledger contents and the same normalized state, ignoring
  `sink_seq` and timestamps (see Tests and evidence).
- A W1 run that executes the effect records `data.decision` on its `effect.request`, equal to the resume value it
  received (**done**).
- In every W1 and W5 history, each `node.start` and `node.end` has a `task_id`, and each `saver.put_writes.call`
  made for a node's task matches that node's `task_id` (**done**).

Evidence: histories and ledgers for each variant, recorded here (see Tests and evidence).
