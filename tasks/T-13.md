## Decisions
1. **One file, two readers.** research/preregistration.md is prose for people and one fenced JSON block for the
   gate, as FROZEN.md is. The block binds; a test checks the cell table in the prose against it. The commit that
   last changed the file is the pre-registration commit.
2. **What a cell fixes.** Its scenario file and content hash, its master seed, N, phase (`instrument` or
   `new-evidence`), evidence class (control, replication of one of the three published results, or new
   evidence), and a prediction per invariant: one value (firm), several (one of them in every trial), `*` for
   every invariant not named, or `NOT_EXERCISED`. VIOLATION is never predicted: the checker never writes it.
   Honestly unknown cells say so; their status is `recorded`, not `differs`.
3. **The frozen checker is pinned in full:** T-10's `checker_sha256`, the sha256 of FROZEN.md's bytes, the
   clause registry's hash, and every effect model's and landmark table's hash by name. The gate compares each
   with what `freeze.verify_checker` returns, and a cell's landmark table must be one of the pinned ones.
4. **The gate** (`authorize_batch`, called by the runner before doctor) refuses unless the checkout is clean; the
   pre-registration is final, committed, and an ancestor of HEAD; the checker is FROZEN, verifies against
   FROZEN.md (T-10's `freeze.verify_checker` with the clause registry's hash), and is the pre-registered one;
   the freeze commit is an ancestor of the pre-registration commit; the scenario's hash, cell, and master seed
   are pre-registered; N is the cell's N; the landmark table verifies; and, for a new-evidence cell, every
   instrument cell came out as predicted, in one environment. It names every failed condition at once.
   `confirm` runs after doctor: the manifest holds the pre-registered environment, names the authorized
   commit, and is clean, and a new-evidence batch's manifest matches the instrument batches' environment in
   every material field that a compatibility rule recorded at the run commit does not cover.
5. **T-07 and T-10 are reached through adapters** that import them lazily, so this lane merges on main without
   them and without touching `checker/` or `orchestrator/`. Without them the gate refuses ("not in this
   checkout"). The landmark step calls T-10's `freeze.verify_scenario`, which reads the scenario's `landmarks`
   key, requires an audited table in FROZEN.md with a matching hash, and returns its sha256; a cell that injects
   a fault must name a table, since every arm is checked against one.
6. **Proof from git, not from the batch.** `verify` checks the run commit against the manifest, ancestry
   (freeze before pre-registration before run), that neither the pre-registration nor FROZEN.md changed before
   the run, every hash, exactly N trials numbered 1 to N, the environment, and each trial's checker.json
   (frozen checker hash, registry, landmark table, FROZEN state, authorized for new evidence; a trial without
   result.json must list what was not exercised). It also recomputes the runner's own records instead of
   reading them: scenario.json must hash to the pre-registered scenario hash, run.json must name the cell, the
   master seed, N, and canonical mode, and every trial seed must equal sha256 of `[master_seed, cell, trial]`,
   computed independently of the runner (a test checks it agrees with the runner's function). A batch whose
   authorization the runner revoked (the checkout changed while it ran, so authorization.json was moved to
   authorization.revoked.json) is refused with the runner's reasons.
7. **cells.json, not summary.json.** T-07's runner already writes a summary.json of trial validity in each raw
   batch; the cell statistics go in cells.json (agreed with the T-07 lane).
8. **Pooling fails closed.** Every manifest field is material except `generated_at`, `git_dirty`, and
   `sink_clock_offset_ns`; the harness commit is material, so batches from different commits pool only under a
   recorded rule. Rules live in research/compatibility.json (none today), each naming a field, both values, and
   a reason, and cells.json lists every rule it applied. Batches pool only with the same pre-registration commit, checker, freeze, and
   scenario, and no material difference a recorded compatibility rule (field, both values, reason) does not
   cover. Otherwise each set is its own group, and the cell names the differing fields. Aggregation refuses
   outright if any batch fails verification.
9. **Counting.** INVALID trials count toward the group's INVALID share only; above 2% the group is excluded. In
   other trials an invariant is its outcome, `NOT_EXERCISED` (listed in checker.json, or no result.json at all),
   or `NOT_EVALUATED`. n counts exercised trials; k counts anomaly outcomes (EXPECTED, GAP, VIOLATION_CANDIDATE,
   VIOLATION). Each invariant carries three separate readings: `unstable` when a deterministic cell's trials do
   not all show one value, `escalate` on any VIOLATION_CANDIDATE, and the prediction (`as-predicted`,
   `differs`, `recorded`, or `missing`). A group's status is the worst of excluded, escalate, unstable,
   differs, missing, recorded, as-predicted.
10. **The draft's cells** follow the methodology I approved on 2026-10-09: C1 for nine workload and durability
    variants and C3 for three workloads at N = 50 (the discovery form of the fault-free controls); C2 (K2), the
    misuse controls K5 and K5-reject, and the replications K1a (#8039), K3 (#8796), K4 (#8764) as the
    instrument; then K1b, N1 to N12, N12b, and A1 to A4 at N = 20 as new evidence (E1 is deferred, decision 12).
    A describes clause never supports PASS; K1b, N4, A2, and A3 predict I2 under LG-PW-CRASH, decision 2's split;
    and a heal after a held response is triggered by a fixed delay, never by the read-only probe.

11. **Rulings of 2026-10-10.** K2's I6a is NO_ANOMALY_UNSPECIFIED or GAP, resolved: C2 forces the fork, not
    which branch the acknowledgments and the head agree on, and alternation across trials makes the cell
    UNSTABLE. K5 and K5-reject predict I4 EXPECTED and I7c NOT_EXERCISED. K5-reject stays. T-09's fault-free
    histories are pre-freeze inputs, never evidence.
12. **Rulings on T-10's readings, applied 2026-10-10** (the pre-registration's "Rulings applied" section). D1: a
    second run never suppresses I1a, I1b, or I11, and still covers I2, I4, and I5-I8, so the retry cells read
    I4 as NO_ANOMALY_UNSPECIFIED or GAP. D2: I4 PASS under LG-PW-EXC needs a node that raised, so the fault-free
    controls, N10, and A4 predict NO_ANOMALY_UNSPECIFIED and no W1 or W5 cell predicts I4 PASS; the controls
    now name I4 apart from `*` so a PASS there differs. P1: K1a, A1, and N3 are GAP on I4 (and K1a and A1 on
    I7a). P2: K4 scores no outcome. P4: K3 and N8 hold a worker at a barrier instead of SIGSTOP. P5: every arm
    names its audited occurrence (L-IN 1, L-RES 2, L-EXW 3, L-EXC 2, L-T1 3, L-GET 1). P6: K1b, N4, A2, and A3
    cite LG-PW-CRASH. E1 leaves the first matrix: under exit durability no `put_writes` happens during a run, so
    L-EXW never occurs, no exit-mode histories exist to derive a landmark, and LG-DUR-EXIT maps to no
    invariant. A1-A4 stay pending: T-09's audited corpus is sync only, so their landmark occurrences under
    async are not audited.
13. **Observations apart from outcomes.** A cell may predict what it observes: effect ledger rows by effect
    (count and attempts, from ledger.json, an export the sink verified), a `checker.json` record that is not an
    outcome (by its leading text and count), or whether an invariant showed any anomaly, whatever its class.
    Each is matched in every valid trial and reported beside the invariants with the trials that did not show
    it and what they showed; it enters the group's status, so an instrument cell is ready only when its
    outcomes and its observations came out as predicted. Every replication must name one: K1a two charge rows
    with attempts 1 and 2 (#8039, though its outcome is GAP), K4 the record of an accepted run with no durable
    record for start-1 (#8764, nothing scored), K3 the fork (#8796). K2, K5, and K5-reject carry theirs too
    (the fork; the precheck and charge rows). The specification's C11 bar is 19 of 20; these cells are
    deterministic, so the gate asks for every valid trial and a split is UNSTABLE, which is stricter.

14. **The frozen checker is pinned (2026-10-10).** T-10 froze checker v1 in 2802584 (#28). Verified from main
    before pinning, not copied: `freeze.verify_checker` accepts the checker files against FROZEN.md with the
    clause registry's hash computed here, FROZEN.md's LF bytes hash to the recorded value, and the freeze commit
    is the one that last changed it. Pinned: checker `d8095168…`, FROZEN.md `ddff87d4…`, registry `0c25b2d9…`,
    effect models w1, w1-misuse, and w5, and the audited landmark table langgraph-v1 `279e5e44…`; the
    environment's `clause_registry_sha256` is the same registry hash, since doctor computes it with the same
    function. A test re-derives every pin from FROZEN.md and the checker files, and another checks K4's
    observed record against the frozen engine's wording. With T-10 on main, the gate imports it directly
    instead of through a lazy adapter; `Unavailable` stays for the adapters the tests substitute.
15. **The TrialScenario builder is pinned (my decision of 2026-10-12).** `orchestrator/declared.py` turns a
    batch's records into the checker's input and is not in FROZEN.md, so the pre-registration pins its file
    by sha256 (`builder`). The gate refuses a batch whose pre-registration commit or run commit holds any
    other version of it, verification refuses such a batch again, and a final pre-registration without the
    pin is incomplete. A test holds the draft's pin to the file's bytes, so a change to the builder fails CI
    until the pin moves with it. It stays outside checker v1; nothing in the freeze changed. The pin covers
    that one file: what it calls (the scenario loader, the dispatcher's fault ids) is bound by the harness
    commit, which is a material fingerprint field.
16. **Every armed step names its landmark (my decision of 2026-10-12).** A scenario step that arms a
    failpoint has a required `landmark:`, the scenario must name its table (`landmarks:`), and loading
    refuses a missing landmark, an unknown one, or one whose method or audited occurrence differs from the
    step's. The table is read with the frozen checker's own loader; no table or landmark definition changed.
    The name is part of the validated model, so it enters the scenario's hash. The builder takes the named
    landmark instead of inferring one and holds it to the table again. Scenarios without armed steps hash as
    before (the four unarmed T-09 scenarios keep their recorded hashes); the smoke scenario's hash moved to
    `de411c3d…` and W5 concurrent's to `378e3071…` (T-09 recorded `ac4cf793…`, pre-freeze input only).
17. **The canonical first-matrix runner is GitHub-hosted Ubuntu 24.04 (my decision of 2026-10-12).** Not yet
    pinned under `environment`; that, with the other environment pins, comes with the final pre-registration.

## Integration contracts (agreed 2026-10-10)
- T-07 (integration on `t-13-run-gate`, stacked on this branch): a batch is gated when its scenario matches a
  committed pre-registration's cell by file path, cell id, or content hash, so a cell cannot dodge the gate by
  moving its file. A gated batch must be `--canonical` and run from its pre-registered file. Before doctor the
  runner calls `experiment.aggregate.authorize(source, trials, root, instrument)`, which builds in the
  instrument check under the rules recorded at HEAD (`crashcourt run --instrument <batch dir>...`); it writes
  authorization.json beside manifest.json; after doctor it calls `confirm(authorization, manifest, root)` and
  refuses the batch on any problem. Ungated batches carry no authorization.json, so verification and aggregation
  never count them. Scenario = one cell; trials numbered 1 to N (`<cell>/trial-0000n/`); scenario.json is the
  canonical JSON the hash is taken over; run.json records the cell, master seed, N, mode, and every trial seed.
- T-10: FROZEN.md at src/crashcourt/checker/FROZEN.md; `freeze.verify_checker(text, registry_sha256)` for the
  checker and `freeze.verify_scenario(text, registry_sha256, scenario_path)` for the landmark table the scenario
  names (scenarios/landmarks/<name>.yaml, status audited); checker.json per trial, always with batch, cell, and
  trial; a trial with no exercised invariant has only checker.json; `observations` in checker.json are
  records that are not outcomes, worded as `engine._observations` writes them. The effect ledger's export is
  `<trial>/ledger.json` (`rows` with T-08's columns, and the sink's `verify_ok`), which T-07's post-trial step
  writes and both the checker and the observations read.
