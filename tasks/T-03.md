## What I found (the audit has the citations)
1. **A put commits in one transaction, and rolls back when the server rejects it.** Blob rows and the checkpoint row
   carry one `xmin` in every tested mode, and a rejected checkpoint row rolls back its blobs. In the pipeline modes, a
   client-side exception between the two statements could still commit the blobs alone: psycopg sends a Sync whenever
   a pipeline block exits. `put_writes`, the pool path, and the no-pipeline fallback are read from code.
2. **Under `sync`, the first tick runs before the input checkpoint is known to be durable.** In a `StateGraph` that
   tick is the internal start step, and user nodes run only after the input and step-0 puts commit; in a
   functional-API entrypoint, user code runs while the input put is in flight (one in-process experiment). A failed
   put followed by a successful one leaves a missing parent under `async` at any step and under `sync` for the first
   puts; on Postgres the later checkpoint can also lack the channels the failed put would have written. These are
   readings to measure with the pinned savers, not findings.
3. **`sync` waits for checkpoints, not for task writes.** A finished node's writes commit in the background, and
   nothing waits for them before the next step, except delta-channel and error-handler writes. `invoke` returns after
   they finish, but streamed chunks arrive before. #8039 reports this ordering.
4. **Six ambiguous-commit windows (AW1 to AW6)** are located for the lost-acknowledgment, connection-reset, and
   database-restart faults: checkpoint put, task writes, resume value, a failed put followed by a successful one, the
   first checkpoint, and a database restart.
5. **The default durability is `async`,** not `sync`.
6. **Watch items.** Draft PR #8838, by a maintainer, adds `queue_state`, a durable per-thread update queue promised
   "exactly once per run"; it is steering, not run serialization. Open PR #9235 (2026-10-07) would stop saving a
   checkpoint past a failed delta-channel write, which narrows AW4 for delta channels.

A second review of those fixes found more, fixed here:
- Section 1 said blobs committed without their checkpoint are orphaned; the next put's checkpoint references them,
  because each put writes only the channels changed since the previous one was submitted. The reverse case is a real
  consequence the audit had missed: if a put rolls back entirely, the next checkpoint on Postgres names blob versions
  that were never written, and those channels drop out of the state read back. Section 7 and AW4 now say so.
- #8039 is credited: it reports that nothing orders a step's `put_writes` before the next `put` under `sync`, and a
  comment there traces the input and step-0 order.
- Section 8 said nothing waits for task writes before the client's result; `invoke` does wait, at executor exit.
- Clause ids from another task were restated from the docs, the async psycopg path and the saver-pipeline Sync are
  cited, AW4 under `sync` is limited to the first puts, a `Command` input writes no input checkpoint, and the search
