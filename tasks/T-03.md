## Findings worth your attention (the audit has the citations)
1. **`put` is atomic, and so is `put_writes`.** Blob rows and the checkpoint row share one transaction in every
   connection mode. A rejected checkpoint row rolls back its blobs. The spec listed this as unverified.
2. **`sync` waits for checkpoints, not for task writes.** A finished node's writes commit in the background, and
   nothing waits for them before the next step, except delta-channel and error-handler writes. This is a code reading
   that bears on LG-PW's "already durable" and on I2; T-12 should measure it.
3. **Six ambiguous-commit windows (AW1 to AW6)** are located for F10, F11, and F13: checkpoint put, task writes,
   resume value, a failed put followed by a successful one (a dangling parent under async durability), the first
   checkpoint, and a database restart.
4. **The default durability is `async`,** not `sync`.
5. **Spec wording that differs from the code** (recorded in the audit, spec unchanged):
   - `AsyncPostgresSaver`'s lock is an `asyncio.Lock`;
   - checkpoint ids are UUIDv6 from each process's wall clock, not ULIDs;
   - a mixed write batch is first-writer-wins even for resume values;
   - the #6985 test #8796 cites is an unmerged SQLite PR.
6. **Watch item.** Draft PR #8838, by a maintainer, adds `queue_state`, a durable per-thread update queue promised
   "exactly once per run". It is steering, not run serialization, so it does not change the thesis; it would be a
   testable guarantee if it lands.
