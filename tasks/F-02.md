## Decisions
1. **Fixtures are the four v1 artifacts and nothing else.** Each batch is `<batch>/manifest.json` and
   `<batch>/batch.json`; each trial is `<batch>/<cell>/<trial>/` with `result.json`, one history per process
   (`orchestrator`, `worker-a`, `worker-b`, `sink`), and `merged.jsonl`, which is the harness's own merger's
   output. The histories copy the shapes T-06 and T-08 record (put fields, put_writes channels and task path,
   effect requests with node and payload hash, sink rows with `seq = sink_seq - 1`) and T-09's
   `data.decision` on W1 effect requests.
2. **Three batches, two demonstration scenarios.** `DEMO-batch-matrix` runs the matrix scenario: C1 (one
   worker, no faults), C2 (two workers held after `get_tuple` and released together, the forced fork), W1-F08
   (conflicting resumes: a fork and an orphaned effect, the one finding), W1-F01 sync and async (SIGKILL after
   the effect, then the re-run), W1-F03 (SIGSTOP and SIGCONT), W1-F11 (timeout toxic, then reset; its second
   trial ends without a terminal client event and is INVALID), W1-F13 (database restart), and W2-F12, the
   randomized cell (a latency toxic fired at a seeded time offset; its third trial saves one child's writes
   twice, a VIOLATION_CANDIDATE). `DEMO-batch-compare-a` and `-b` run the compare scenario (W1-F05, a stale
   worker) against two demo runtimes: A saves the stale write, B refuses it. Every fault mark the explorer
   draws is in a merged history, and every outcome except VIOLATION appears.
3. **What v1 cannot carry.** v1 has no summary record (T-13 writes `summary.json`), so nothing in the
   fixtures states k/N, intervals, or whether a control passed; the overview's counts stay dashes. Cell
   metadata lives where the harness would put it: the cell id reads `DEMO-[control-]<target>-<durability>-
   <workload>-<fault>[-rand]`, after T-04's sample, and a randomized cell's `fault.inject` names its seeded
   offset (`data.trigger.offset_ns`) where a deterministic cell's names a failpoint or a barrier. The site
   parses neither.
4. **Ids.** Every identifier starts with DEMO-: batch, cell, op, logical op, thread, checkpoint, parent, task,
   effect key, fault, invariant, clause, repro, and evidence paths, plus the manifest's commit, lockfile,
   clause registry, spec hash, images, and package names. Process names, failpoint names, and seeds are not
   ids and are as the harness writes them. The runtimes are `DEMO-runtime-a` and `DEMO-runtime-b`, so no
   fixture describes a real system's behavior.
5. **No VIOLATION.** A VIOLATION needs a human review, which a fixture cannot have, so none is generated.
   Every fixture outcome's note says "Demo data, not a result: written by crashcourt fixtures --demo, not
   measured."
6. **Determinism.** The output depends only on the seed (default 1): clocks, pids, and trial seeds come from
   sha256, and a trial's seed is `sha256(master, cell, trial)`. `wall_ns` starts at 1.8e18 (2027-01-15), and
   `mono_ns` at about 107 days of uptime, past 2^53, so both clocks use the site's exact-integer path.
   `scenario_sha256` is `content_sha256` of the demonstration scenario's model, so it does not change with
   the seed and is never typed in.
7. **Evidence pointers** are `<cell>/<trial>/merged.jsonl#/<index>` relative to the batch, a JSON pointer
   into the history read as an array, as tests/unit/test_records.py already writes them.
8. **The banner keys off provenance.** Every value a page renders comes from `lib/batches.ts` with the
   provenance of its records, and `DemoBanner` shows when any source is a fixture; there is no route list,
   build flag, or environment variable involved. It is a server component (no JavaScript, and its marker
   reaches the export only on pages that render it), has nothing to press, and stays pinned to the top of the
   window. It is an inverted band, not the accent, which DESIGN.md reserves for faults and focus.
9. **Rules that span files** are checked for every build, not only releases: each top-level directory is a
   batch with both records; the batch's `manifest_sha256` is its manifest's sha256; a result names its batch,
   that manifest hash, and that provenance; every event names its trial; histories sit beside a
   `result.json`; batch ids and trial pages are unique. Route ids: trials by cell and number, lineage by
   `<cell>.<trial>` and thread, a finding by the last segment of its repro reference (until T-14 writes
   finding records), compare by scenario hash.
10. **Compare.** A dev build shows a scenario that batches pinning different runtimes ran. A release build
    exports only the placeholder, always: v1 does not name a batch's target, so a release cannot establish
    that two targets have validated runs, and the guard fails any other compare page. Naming the target needs
    a schema change (asked on #19; settled below).
11. **The release guard.** Input: `results/` holds at least one batch (else it fails closed), passes v1 and
    the cross-file rules, says `run` in every record, holds no "DEMO-" in any byte, and names no committed
    fixture's scenario or manifest hash. The guard reads `site/fixtures/` for those hashes; the build never
    does. Output: no "DEMO-", no banner marker, no serialized fixture provenance, and no compare page beyond
    the placeholder.
12. **One release build.** `npm run build:release` sets `CRASHCOURT_RELEASE=1`, under which `artifactRoot`
    returns `../results` and refuses `CRASHCOURT_ARTIFACTS`; the loader then refuses an empty batch list or
    any record that is not a run, before any page renders. Steps: schema and verdict checks, input guard,
    a fresh export, the Windows post-build fix-up, output guard.
13. **Proving the guard.** `site/tests/release/cases.ts` holds a clean self-test batch (the matrix fixture
    with ids renamed `selftest-`, provenance `run`, its own scenario hash, hashes recomputed) that the guard
    must pass, and six planted cases it must refuse: a fixture as is, one DEMO- id in a run batch, a renamed
    fixture keeping its scenario hash, a changed manifest, a result from another manifest, and no batch. The
    unit tests run them against the guard; `site-release.yml`'s guard-proof job runs each through the real
    release build and checks the output guard refuses a fixture build. The self-test batch exists only in
    temporary directories. The release job builds from the commit's `results/` on tags and manual runs, and on
    a pull request whenever `results/` holds files: the deliberately failing run below planted a fixture
    there.
14. **Browser tests never reuse a server.** Playwright reused a server left on port 4173 by another worktree,
    so a first run checked F-01's build and passed on 404 pages. The server now always starts fresh, the port
    is `CRASHCOURT_E2E_PORT` (default 4173), and the banner test checks each page's status.
15. **Lighthouse locally.** With other sessions loading the machine, total blocking time on `/` ranged from
    97 to 1,108 ms on identical JavaScript. CI's Linux runner is the gate, as for F-01.
16. **Long ids wrap.** A 64-character seed overflowed the trial page at 1280 pixels and a scenario hash the
    compare page on a phone; readouts and routes now wrap anywhere, and every exported page is checked for
    sideways scroll at both widths.
