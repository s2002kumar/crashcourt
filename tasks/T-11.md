## The card (issue #30)

### Objective

Prove that the instrument catches known injected defects before any new evidence is allowed: the saver mutants M1-M5 (control C5), the placebo control's armed failpoints that do nothing and its zero-latency toxic (C3), and one redelivery primitive, so the K1a (langgraph#8039) and K3 (langgraph#8796) instrument cells can be written and run.

### Reason

Nothing is publishable without passing controls (gate G1). The pre-registration's run order already refuses new evidence until every instrument cell has come out as predicted; this task gives the instrument cells and checks that are still missing a way to run, and makes the gate read C5's result instead of trusting free text.

### Scope

In scope:

- C5: labeled saver mutants M1-M5, each judged by its target invariant at the pre-registered threshold (at least 19 of 20 trials).
- C3: failpoints armed with action `none`, and a whole-trial zero-latency latency toxic on each worker's proxy.
- One generic redelivery/takeover primitive, enough for K1a and K3 and reusable by T-12 for K1b, N8, N11, A1, and A2.
- Whatever the existing gate needs to consume these results, and tests that a failed or missing control blocks new evidence.

Not in scope: T-12's fault schedules (client retry, database restart, a second resume, the other network toxics), the first trustworthy batch, and writing or finalizing the pre-registration's scenario files.

### Deliverables

- `tests/mutants/savers.py`: M1-M5, test-only, each a labeled subclass of the pinned `AsyncPostgresSaver`. The worker loads one only when the runner is given it for an ungated, non-canonical batch; `run.json` and `trial.json` name it.
- A C5 driver that runs each mutant for 20 trials on the real stack, judges every trial with frozen checker v1, and writes a controls report (JSON) and a one-page summary.
- Scenario support: failpoint action `none`; a whole-trial `latency` toxic of 0 ms and 0 jitter per worker; a `redeliver` action, with an `exited` trigger (the worker's replacement takes the op) and an `ended` trigger (release a held stale worker once the redelivered op ends). Scenarios that use none of them keep their content hashes.
- Runner and engine support for the above; the trial-scenario builder maps a `none` arm to no fault and a redelivery to the frozen checker's `redelivery` fault.
- Gate integration: a new-evidence batch is refused unless the pre-registration's C5 instrument check names a committed controls report that shows every mutant caught at the threshold under the pinned checker. C3, K1a, and K3 are instrument cells, which the existing instrument check already requires.

### Mutants and their target invariants (stated before any mutant runs)

Every mutant runs in the same shape: W1 approve, sync, one worker, no fault (C1's shape).

| Mutant | Defect | Target invariant |
| --- | --- | --- |
| M1 | a `put_writes` call that writes two or more rows does not store its second row (the specification's "drops the second `put_writes` row") | I7a |
| M2 | `get_tuple` by checkpoint id returns `None` | I5a |
| M3 | `put` stores no parent | I5a |
| M4 | the second `put` of each op is written in a transaction whose commit fails; the error is swallowed and the put reports success | I1b |
| M5 | the latest-checkpoint read returns the head's parent | I6b |

Caught: the trial is valid (no INVALID trigger) and checker.json shows an anomaly on the target invariant (EXPECTED, GAP, or VIOLATION_CANDIDATE). Threshold: at least 19 of 20.

A risk I can state before running anything: W1 and W5 may never read back a dropped `put_writes` row, and nothing in them reads a checkpoint by id. LangGraph 1.2.12 reads by id only when the caller passes a `checkpoint_id`, and our runs never do. A pending write is read back only after a crash that follows its commit, which is the question K1b, N11, and A2 ask. If M1 or M2 is not caught, C5 fails as specified and I decide what follows; nothing here changes a definition or the threshold.

## Design decisions

1. **Redelivery keeps the op.** A redelivered op keeps its id and its single `client.invoke`; its terminal
   event is the new worker's result. That is what checker v1 already models: `dispatch.redeliver` with the
   same op id and `data.to`, a `redelivery` fault naming the op and the worker, and the merge's dispatch edge
   for either kind of dispatch. Nothing in the checker changed.
2. **Two new triggers, one new action.** `exited: w` redelivers the op the step that ends `w` was in (K1a, K1b, N11,
   A1, A2: a kill at a failpoint, then the replacement). `all_paused` redelivers the op its barrier holds,
   and `ended: op` releases that stale run once the op has ended (K3, N8). Loading refuses any redelivery
   whose op is not certain to be in flight when it fires, a target a step could end, an op redelivered
   twice, and a release after an op ends whose barrier is not certain to hold that op's stale run.
3. **Stale runs.** A result from the worker an op was taken from is noted in trial.json, never a client event.
   The trial waits for a released stale run (K3's fork lands only if it does), for at most the run timeout;
   past it, the trial is invalid because a timer decided what followed. A stale run never released is left
   held, as any parked run is at shutdown.
4. **The placebo toxic is not a fault.** v1 has no fault kind for a toxic that delays nothing, and an
   undeclared `fault.inject` is INVALID (trigger 9). So the runner installs it before any worker starts,
   reads it back from Toxiproxy, removes it after every worker has exited (before the snapshot, which must
   find none), and records all of it in trial.json; a toxic not confirmed is a reason the trial is invalid
   (trigger 16 for the checker).
5. **Mutants stay test code.** The worker imports `tests.mutants.savers` only when the runner names a mutant,
   which it refuses for canonical batches, pre-registered scenarios, and output under results/.
6. **The gate reads C5, not a sentence.** The pre-registration's C5 instrument check names a report path. Before
   any new-evidence batch, the existing instrument check reads that report as committed in the
   pre-registration commit and refuses unless it holds exactly the methodology's applicable mutants, each on
   its shape and target and recounting to at least 19 of 20, and exactly its exclusions, as NOT_EXERCISED;
   states the pre-registration's requirement word for word; ran under the pinned checker; ran the committed
   mutants, driver, and shapes; and ran in the pre-registered environment. Its `applicable_passed` field
   must agree with its counts and is never trusted alone; it says nothing of the exclusions.
7. **Hashes stay put.** `toxics` is left out of a scenario's hashed form while empty (`OMIT_WHEN_EMPTY`), so
   T-09's recorded scenario hashes still verify; the new actions and triggers are new union members, present
   only when used. #31 then made every armed step name its landmark, which does enter the hash: the shapes
   name theirs, and w5-concurrent's recorded hash changed there, not here.
8. **The builder pin moves with the builder.** #31 pins `orchestrator/declared.py` in the draft
   pre-registration; this PR changes that file (inert arms, redelivery faults), so it updates the pin in the
   same commit, as the draft's rule asks.

The original C5 failure stays as it was measured. It was a failed instrument-design check before the
pre-registration was final, not a finding about LangGraph: M1 and M2 are not exercised by the first matrix's
workloads, and W1 is the wrong workload for M5. The first matrix's C5 is:

- M3 on W1 approve, caught by I5a in at least 19 of 20;
- M4 on W1 approve, caught by I1b in at least 19 of 20;
- M5 on W5 sequential, caught by I6b in at least 19 of 20;

## The `workers` field: audit for T-13

`Cell.workers` (`int`, 1 or 2) has no definition in the model or the prose; the cell table shows it as
"Workers". The red-team specification's table, which the cells come from, wrote K1a's as "1 (+replacement)"
and K1b's as "1 (+r)"; the pre-registration's integer dropped the replacement. The gate never compares it
with the scenario.

In the harness a redelivery goes to another worker the scenario declares (its own process, proxy, and
history; loading refuses a redelivery to the same worker or to one not declared), so every redelivery cell's
scenario declares two workers. Read as worker processes, the field is wrong in five cells:

| Cell | Phase | `workers` | Scenario needs | Why |
| --- | --- | --- | --- | --- |
| K1a | instrument | 1 | 2 | resume-1 redelivered to the killed worker's replacement |
| K1b | new evidence | 1 | 2 | resume-1 redelivered after the kill |
| N11 | new evidence | 1 | 2 | resume-1 redelivered after the kill |
| A1 | new evidence | 1 | 2 | K1a under async |
| A2 | new evidence | 1 | 2 | K1b under async |

Consistent: K3 and N8 (2: A held, B takes the op over), K2, N5, and N6 (2, concurrent). The retry cells
(N1-N4, N9, A3) send resume-2 as a client retry, not a redelivery; N1's trigger names A's proxy, but N2-N4,
N9, and A3 do not name the worker resume-2 goes to, and 1 is right only if it is the same one. Read instead
as concurrent writers, the five cells are consistent at 1, but then the field needs that definition and still
cannot be checked against a scenario. T-13 owns the correction; nothing here changes a cell.

semantics, C3's inert arms are checked like any arm, and the revised C5 runs on v1 unchanged. Noted, not

  By my ruling I3 is not narrowed; M5 runs on W5, where I6b catches it.
- **C3's toxic.** v1 has no fault kind for a toxic that delays nothing, and any undeclared `fault.inject` is

  the checker verify it from the histories.

Also noted, not a checker matter: trial.json's `steps.barrier_fired` now lists every orchestrator step that
fired (`exited` and `ended` steps too); the key keeps its name so the record's form does not change.
