## Decisions
1. **The envelope has the card's identifiers, `effect_key` among them.** It sits after `attempt`. Every line carries
   every field, null where it does not apply.
2. **Kinds are exactly the card's families, 30 in all.** `saver.<method>.{call,return,raise}` covers the four methods
   the failpoint saver wraps (`put`, `put_writes`, `get_tuple`, `list`); async methods log under the same names. No
   kind was added.
3. **Choices the card leaves open:**
   - `status` is `ok`, `fail`, or `info`;
   - `attempt` starts at 1 (LangGraph's `node_attempt` does too);
   - `trial`, `seq`, and `pid` are non-negative;
   - integers are strict (a boolean is not a seq), and a schema version is the integer 1, not `true` or `1.0`;
   - an `effect.response` always has a status.
4. **Cross-process edges come from `data`, not new envelope fields.** Kinds the merger links must carry what it needs,
   checked when an event is loaded:
   - dispatches name the worker (`data.to`);
   - releases name the paused hit (`data.proc`, `data.hit_seq`);
   - actions name their hit (`data.hit_seq`);
   - sink appends name the worker and the ledger row (`data.worker`, `data.sink_seq`);
   - ok effect responses name the row they were acknowledged with (`data.sink_seq`);
   - exits name the process (`data.proc`).

   JSON Schema cannot express these rules, and the schema's description says so.
5. **The effect edge follows the ledger row.** Each `sink.append` precedes the ok `effect.response` naming its row. A
   failed response names no row and gets no edge, so a failure followed by a successful retry keeps its order. The
   merge rejects, as a history that contradicts itself:
   - an ok response whose row the sink's history does not hold, or with no sink history at all;
   - an ok response whose row the sink appended for another worker, operation, key, or attempt;
   - a ledger row appended twice.

   Both effect edges rest on write order, now stated in events.py: the worker logs a request before sending it, and
   the sink logs an append after the row commits and before it answers. T-08's sink has to keep that order.
6. **A result edge.** The merger's first sample showed a `client.ok` placed before the worker had started, which is
   causally allowed when nothing links a result to the work behind it. A worker knows its own last `seq` when it sends a
   result, so `client.ok` and `client.fail` may carry `data.worker` and `data.worker_seq`, and the merger orders that
   worker event first. T-07's control protocol should fill them in.
7. **Two tempting edges are left out because they can be false.**
   - `worker.start` before the worker's first event: a child can log before the parent records the spawn.
   - Every worker event before `client.ok`: background saver writes can finish after the result.
8. **The barrier edge's assumption is written down.** For a pause, the failpoint saver writes `fp.action` only after
   the orchestrator's `fp.release`; events.py says so, since a writer that logged the action first would break the
   edge.
9. **Records.** `batch.json` and `result.json` carry `provenance` (`run` or `fixture`) and the sha256 of the batch's
   manifest; a batch id starts with `DEMO-` exactly when the record is a fixture. A result holds exactly one outcome
   per invariant: the five verdicts, plus `VIOLATION_CANDIDATE` (a clause forbids the anomaly; the repro and review are
   still to come) and `NO_ANOMALY_UNSPECIFIED` (no anomaly and no clause). They are separate values, compared whole,
   so neither is a VIOLATION or a PASS. What each outcome needs:

   | Outcome | clause | evidence | repro | review |
   | --- | --- | --- | --- | --- |
   | PASS | required | optional | none | none |
   | EXPECTED | required | required | optional | none |
   | GAP | none | required | optional | none |
   | VIOLATION_CANDIDATE | required | required | optional | none |
   | VIOLATION | required | required | required | required |
   | NO_ANOMALY_UNSPECIFIED | none | optional | none | none |
   | INVALID | optional | optional | none | none |

   INVALID also needs a reason. EXPECTED, GAP, and both kinds of violation describe an observed anomaly, so they cite
   evidence for it. Identifiers have no whitespace, text is trimmed, and a review date is a real date. The records
   hold outcomes; nothing here computes them.
10. **v1 is frozen by hash.** A test pins the sha256 of each committed v1 file. Model docstrings render into the
    schemas, so editing one on a v1 model, like changing a field, needs a v2. If a Pydantic upgrade renders the models
    differently, the export check fails and the committed v1 files remain the contract.
11. **The record schemas carry the rules.** The outcome table is in `result.json` as `if`/`then` rules under
    `allOf`, and the `DEMO-` rule as `if`/`then`/`else` in both record schemas, so a reader that validates with JSON
    Schema alone (the evidence explorer) rejects what the models reject. Two rules stay in the models only: one
    outcome per invariant, and a result's manifest hash matching its batch's; the descriptions say so. Python has no
    JSON Schema validator in the lock, so the two sides are tied by a shared case file, tests/data/records-v1.json:
    the models' test checks every case here, and the explorer's Ajv test checks every case the schemas cover.
12. **Windows clock.** Windows has no `CLOCK_MONOTONIC`, and `time.monotonic()` there is `GetTickCount64()` with
    15.6 ms resolution, which made most sample events tie. The writer uses `clock_gettime_ns(CLOCK_MONOTONIC)` wherever
    it exists (Linux, macOS) and `perf_counter_ns()` (QueryPerformanceCounter, 100 ns, system-wide) on Windows.
13. **Durability of a line.** One `os.write` per event on an `O_APPEND` descriptor opened with `O_EXCL`, so a second
    writer cannot share or truncate a file. There is no fsync: trials kill processes, not the host.
14. **The kill test is in the integration tier.** It spawns real processes, so it runs in CI's Linux job. The
    `integration` marker's description now says "real OS processes, Docker, or the compose services".
15. **The manifest model is strict.** It rejects unknown fields and any `schema_version` other than the integer 1. Its
    JSON form is unchanged.
16. **`.gitignore` anchored.** The pattern `manifest.json` also matched `schemas/v1/manifest.json`, so CI's first run
    failed the schema check on a file that was never committed. It is now `/manifest.json`.
17. **A T-04 reference manifest.** `spec_sha256` is a pinned field, so CI compares against
    research/evidence/t-04/manifest-local.json, recorded from a clean local checkout. It differs from T-02's in the
    two fields below.
18. **The spec's hash is in every manifest.** The specification is private, so its sha256 is committed in
    `spec-provenance.json` (with its version, lock date, and size), and doctor records it as `spec_sha256`. Where the
    spec itself is present, doctor checks that it still matches (verified against the locked file on 2026-10-09); in
    CI and in worktrees it is not, and doctor says so. The hash is provenance: it identifies the specification without
    making it public or a run reproducible from it, and the file and the schema description say so. It is pinned, so
    batches built against different specifications fail the C7 comparison. T-01's and T-02's reference manifests
    predate the field and stay as records of their tasks.
19. **The sink's clock offset is in every manifest.** `sink_clock_offset_ns` is the effect sink's monotonic clock
    minus the host's, as doctor measures it, or null when no sink was checked (T-04 has none; T-08's doctor fills
    it). Each batch gets a manifest, so each batch records its offset. It is recorded, not compared, and never used
    to order events. What a batch does with it (ordinary runs record it; canonical benchmark runs fail closed above
    a threshold) belongs to the runner's preflight (T-07), not here.

## Decisions on the record design (2026-10-09)
Approved: `VIOLATION_CANDIDATE` stays distinct from `VIOLATION`, `NO_ANOMALY_UNSPECIFIED` from `PASS`; `EXPECTED` and
`GAP` require evidence; the v1 files stay hash-pinned. One change before v1 freezes: the manifest records the spec's
hash (decision 18). The sink's clock offset is recorded in every batch (decision 19), and canonical benchmark runs
fail closed above a threshold, which the runner's preflight implements.

## Review fixes
The review of 74fa341 (2026-10-08) asked for five changes and two smaller ones:

1. **Records for artifacts.** Added `batch.json` and `result.json` (decision 9).
2. **The effect edge on a failed response.** The merge linked the first append to the first response for a key,
   whatever its status, so a failure followed by a retry was reordered. It now links on the row an ok response names
   (decision 5).
3. **The barrier assumption** is in events.py (decision 8).
4. **The kill test** now has the child print each seq `emit` returned and requires all of them in the file, with at
   most one more; on Linux it checks the exit status is -9. kill_test.py records one run's counts.
5. **Pinned v1 hashes** (decision 10).

Smaller: the property test records each edge kind with `hypothesis.event`, and the sample history has a lost
acknowledgment (op-9: the sink records the effect, the worker sees a reset, `client.fail`) and a worker killed while
writing a checkpoint (op-10, `client.info`).

Also fixed: `schemas/v1/manifest.json` predated the rebase onto T-02 and lacked three fields; docstrings and test names
referred to section numbers of a document that is not in the repository; the first T-04 reference manifest recorded
an older lockfile and was removed (a new one came with the spec hash, decision 17).

A second review of these fixes, before v1 freezes, found more, fixed here:
- The merge took an ok response's row on trust: a row appended for another request, or a row appended twice, drew a
  false edge. Both are now rejected (decision 5).
- The effect edges' write-order assumptions were only in a merge comment; events.py states them (decision 5).
- A result could hold two outcomes for one invariant, GAP and EXPECTED needed no evidence, a review or repro was
  accepted on outcomes that cannot have one, blank text and impossible dates were accepted, and provenance was not tied
  to the `DEMO-` prefix (decision 9).
- The record schemas did not say that the outcome rules are enforced only by the models (decision 11, since
  replaced: the schemas now carry them).
- An `effect.response` without a status was accepted and silently got no edge.
- The sample's op-9 failed before reaching the sink, a shape the completeness checks would reject; it is now a lost
  acknowledgment, which also shows the case the merge fix is about.
- kill_test.py checks the at-most-one bound per kill and, on Linux, the exit status, like the integration test.

The explorer's review then showed the cost of leaving the rules out: its JSON Schema check accepted a VIOLATION with
no clause, repro, or review, and a `DEMO-` batch labeled `run`. The rules are now in the schemas (decision 11), and the
v1 pins moved with them.
