# T-07 · Worker, control protocol, orchestrator core

Objective: the orchestrator spawns two worker processes, dispatches runs to them, holds and releases them at
failpoint barriers, and records what the client saw; workers run graphs through the wrapped saver and report back

## Decisions
1. **Control protocol.** The orchestrator listens on one Unix socket per worker in a private (0700) directory with a
   short path (socket paths are limited to about 107 bytes), accepts exactly one connection, and checks the kernel's
   peer credentials (`SO_PEERCRED`) against the pid it spawned before reading the hello. Messages are Pydantic models,
   one compact JSON object per line; each side accepts only its own message types, so a worker that sends `run` has
   broken the protocol. A line cut off by the end of the stream is what a process killed mid-write leaves: it is
   reported as such, never parsed. A line over 1 MiB, invalid JSON, an unknown type, or an invalid field is a
   violation; the orchestrator records it, drops the connection, and kills the worker, and the trial is INVALID.
   The orchestrator writes through a duplicate of the socket (`Channel`): an asyncio stream that fails a write
   closes its transport and drops what it has not read yet, so writing to a worker that had just died could have
   lost the result it sent before dying (shown on Linux; a test now covers it). Arms need no acknowledgment: the socket is ordered and the worker applies each message before reading the next,
   so every arm is installed before the first run arrives.
2. **The client view.** For each op the orchestrator writes `client.invoke` and `dispatch.send`, then sends the run;
   the tests check that those two are the last events in the file when the run leaves. Exactly one terminal event
   follows: `client.ok` or `client.fail` from the result, `client.info` when none came back. A result carries
   `worker_seq`, the worker's last written seq when it sent the result (`HistoryWriter.last_seq`); `client.ok` and
   `client.fail` name the worker and that seq together, as schema v1 requires, or neither when the worker had
   written nothing. A run past its timeout ends as info; a result that arrives after that is recorded in trial.json
   as late, never as a second terminal event. `fail` means the client received an error, not that the run
   changed nothing: a run can commit and then lose its acknowledgment, and only the oracle says what happened (the
   card defines fail this way, and the frozen methodology's predictions use it). An error while building a completed
   run's report is the worker's own: it exits with status 5 rather than report a failure; so does a history write
   that failed during the run (the saver's events are written inside it, so the failure would otherwise surface
   as the run's error). A second result for an op, or a result for an op never sent to that
   worker, is a violation. An op whose worker is gone by the time its turn comes is never sent and has no client
   events: nothing was invoked.
3. **A dead worker's ops end as info only once both ends agree.** The engine waits for the control connection's end
   of stream (so every result the worker sent before dying is read first) and for waitpid's status, then writes
   `worker.exit` and an info event per unanswered op whose reason names how the worker ended. Either one alone starts
   a bounded wait (`shutdown_s`); past it the worker is SIGKILLed and the trial says so, and if even SIGKILL does not
   end it, the engine stops waiting and the trial is INVALID. Nothing waits without a bound.
4. **Barriers and schedules.** A failpoint step's action runs in the worker: `pause: <barrier>`, `signal: <name>`, or
   `exit: <status>` (T-06's arms). An `all_paused` step fires once, in the orchestrator, when every barrier it names is
   held at the same time; its action is `release` (all `fp.release` events are written before any release message is
   sent) or `kill: <worker>` (T-05's SIGKILL, recorded as `fault.inject` and `fault.heal`). Hits map to barriers by
   worker, point, op, and occurrence; a hit no step pauses, or a barrier held twice, is a violation. Nothing is
   ordered by time. A run that passes its timeout while parked at a barrier nothing releases cannot move, so giving
   up on it orders nothing. A run that passes its timeout while still running, or is released after its client gave
   up, races whatever was sent next; a timer decided that order, so the trial is INVALID. (A client retry after a
   timeout, F09, needs a release that waits for the retry; scenarios cannot express that yet, and its task extends
   both this rule and the loader's.)
5. **Loading refuses what cannot run as declared**, with every problem at once, before any process starts: unknown
   failpoints, workers, ops, and barriers; an op that runs after a later op; a failpoint step on a worker its op is
   not sent to; two steps that could fire on one call (including a step for any op that is not alone at its point);
   a barrier declared or released twice; a release of a barrier its trigger does not hold; barriers that must be held
   together whose ops are ordered one after the other; SIGSTOP at a failpoint, which nothing can continue yet; more
   than two workers; a worker with no op; a non-finite number anywhere. And schedules whose outcome would depend on
   which of two concurrent hits came first: a barrier named by two triggers (the first to fire could release it
   before the other is complete, or release and kill it in either order); a kill that does not hold one of the
   killed worker's calls by op; a worker ended by a step (a kill, or a signal or exit at a failpoint) that has any
   op not ordered before the call that ends it; a worker ended by more than one step. Calls the ending op itself
   makes concurrently are not pinned by this: under sync durability LangGraph writes a step's pending writes beside
   its checkpoint, so a worker killed at `put.before` may have a `put_writes` in flight. trial.json lists every saver
   call still in flight when a step ended a worker; whether it committed is the snapshot's to say (T-10), and a cell
   that depends on it pins it with a barrier of its own.
6. **Scenario form and hash.** `after` is required on every op (`start` or an earlier op), so equivalent YAML cannot
   state one order two ways and hash differently. `v: 1` versions the format and enters the hash. Scenario YAML reads
   booleans as YAML 1.2 does: PyYAML follows YAML 1.1, where `on:` (the spec's schedule key) loads as `True`. Each
   trial runs a scenario thread as `<batch>/<cell>/<trial>/<thread>`, so no two trials share a thread. A trial's seed
   is the sha256 of the JSON array `[master, cell, trial]`, which keeps the parts apart.
7. **Batch files.** Each batch directory gets doctor's manifest (which carries the clause registry's sha256 and the
   sink's clock offset), the v1 batch record (provenance `run`, the manifest's sha256, the scenario's content hash),
   the scenario in canonical form and as given, and run.json (mode, trials, every trial's seed, each worker's route,
   the pool settings, the sink's health and expected source, the clock check). Each trial directory gets every
   process's history, the merged history, the workers' logs, and trial.json. Batch ids are never reused, are
   path-safe, and never start with `DEMO-`. run.json records options, not the command line, and the scenario file
   relative to the checkout, so no batch file carries a home directory.
8. **Topology.** Worker n connects through its own proxy `postgres-wn` on its own port (15433, 15434; overridable with
   `CRASHCOURT_WORKER_PROXY_PORTS`), created if missing and refused if it listens elsewhere; each trial starts only if
   every route is enabled and has no toxics. A worker's DSN is rebuilt from the target's parameters with every address
   parameter replaced (psycopg's `make_conninfo(..., hostaddr=None)` keeps an existing `hostaddr`), and libpq's address
   variables (`PGHOSTADDR`, `PGSERVICE`, and the rest) are removed from its environment, so nothing can route it around
   its proxy. Pools use the saver's settings (`autocommit=True`, `prepare_threshold=0`, `dict_row`, as its
   `from_conn_string` does). The saver's tables are set up once per batch on the direct path.
9. **The sink.** Before the batch, `/health` must report status ok, ledger v2, no test hook, no resume error, and the
   source hash of the checkout the manifest describes (a dirty checkout is allowed only outside canonical mode, and the
   manifest says it is dirty). The runner rereads `/health` after every trial: a sink rebuilt or restarted mid-batch
   fails the trials after it. Each trial is opened on the sink with its batch, cell, trial, and seed; its ledger's
   hash chain is verified afterwards, and its rows become the sink's history. `/health` now reports the sink's pid,
   which that history needs.
10. **Clock policy.** The limit is one second, from the frozen methodology's environment controls. A canonical batch
    (`--canonical`) refuses to start if the offset doctor recorded in the manifest, or the one measured at batch
    start, is missing or beyond it; an ordinary batch records the warning in run.json and prints it. Neither offset is
    ever used to order events: the merge orders by causal edges and uses `mono_ns` only to break ties, and wall clocks
    are never consulted. Under WSL2 the sink and the workers share a kernel, so the offset is about a millisecond.
11. **Validity.** A trial is valid when every history parses (a partial last line only from a worker that died by
    signal or failpoint), the merge finds no contradiction, every `client.invoke` has exactly one terminal event (read
    back from the file, independently of the engine's bookkeeping), every scheduled step fired, nothing broke the
    protocol, the sink stayed fit, and every worker's exit is explained: shut down with status 0, killed by its step
    with SIGKILL, or ended by its failpoint step with the status that step implies. Any other ending makes the trial
    INVALID: harness statuses (2 protocol, 3 startup, 4 orphaned, 5 the worker's own code), and anything else, such as
    the OOM killer, because every run gets a result unless a scheduled fault ends its worker. `crashcourt run` exits
    0 only when every trial is valid. Validity says nothing about the target.
12. **Linux only.** `crashcourt run` refuses any other host before loading anything, pointing Windows to WSL2 and
    other hosts to a Linux container; workers are spawned in their own session, so a terminal Ctrl-C reaches only the
    orchestrator. A target database that is not on this host needs `--i-own-this-database` (spec section 23).
13. **A run parked for good.** A worker asked to shut down while a run is still in flight (it timed out, or is parked
    at a barrier nothing releases) abandons it: it closes its history and exits 0 at once, rather than waiting on a
    barrier thread forever.
14. **Every trial starts fresh.** Thread ids embed the batch, so a reused batch id would put a trial on another
    batch's threads and ledger: it would continue their checkpoints and append to their ledger file, and still look
    valid (seen during T-09 development, with `--batch` given twice and the output directory removed between runs).
    Before dispatching anything, a trial requires its sink ledger to be empty and the saver's tables
    (`checkpoints`, `checkpoint_writes`, `checkpoint_blobs`) to hold no row for any of its threads; otherwise it is
    INVALID and nothing runs. The check reads row counts on the direct path, before the trial; nothing reads the
    target database to decide an outcome. This is the methodology's pre-trial emptiness control.
15. **CI** runs the 50-trial smoke batch on every push, after the fault self-test, and uploads it with the other
    doctor evidence; the doctor job's limit is now 25 minutes.

Observed while testing, recorded for T-10 and not a finding: under `durability="sync"`, LangGraph 1.2.12 calls
`put_writes` while the step's `put` is still in flight, so a worker parked at `put.before` can still log a
`saver.put_writes.call`.

## Review fixes
An independent review of the implementation found five defects, all fixed here with tests:
1. A worker exit the schedule did not explain (an OOM kill, say) left the trial valid and only "unclean". Now it is
   INVALID (decision 11); the separate flag is gone.
2. A run past its timeout that was still running let the next op race it, and the trial stayed valid. Now that is
   INVALID; a run parked for good may still time out (decision 4).
3. An error while reporting a completed run (its summary) was reported as a failed run. Now it is a harness exit,
   status 5 (decision 2). The broader suggestion, to report errors after a run's first write as info, was not taken:
   it contradicts the card's definition of fail; decision 2 states what fail means instead.
4. A failed write to a worker that had just died could drop the result it sent before dying (decision 1).
5. Scenario loading accepted schedules whose outcome depended on the order of hits (decision 5).

A second review of those fixes found three more, also fixed with tests: a run that timed out while parked and was
released later stayed valid (decision 4); a history write that failed during a run became the run's failure
(decision 2); and a worker could be ended by two steps, of which only one can act (decision 5). It also noted that
calls an op makes concurrently can be in flight when a step ends its worker; those are now recorded in trial.json
rather than judged, since that race is the target's, not the harness's (decision 5). A suggestion to accept ops
ordered after a worker's ending call (they are never sent) was not taken: refusing them is conservative and keeps
the timeout edge case out.

## Card (issue #17)
Deliverables:
- `orchestrator/runner.py`, `orchestrator/dispatcher.py`, `orchestrator/barriers.py`, and `worker/main.py` (**done**;
  also `orchestrator/workers.py` and `orchestrator/topology.py`).
- Control protocol: JSON lines over one Unix socket per worker, with the messages `hello`, `run`, `arm`, `hit`,
  `release`, `result`, and `shutdown`. Every `run` gets exactly one `result` unless the worker dies (**done**).
- Client view: log `client.invoke` before sending a run, then exactly one terminal event. `client.ok` when the result
  succeeded, `client.fail` when the result carried an error, and `client.info` when no result came back (worker
  death, timeout, lost socket). An unknown outcome is never recorded as `fail` (**done**).
- Orchestrator events through the T-04 writer: `dispatch.send`, `worker.start`, `worker.exit` (exit code or signal,
  from `waitpid`), and `fp.release`. The worker logs `fp.hit` before it reports the hit (**done**).
- Barriers: pause a worker at a failpoint matched by worker, operation, and occurrence; release one worker or several
  at once; an `all_paused` trigger that fires once every named barrier is held (**done**).
- Scenario and schedule models in `spec/` (extend what T-04 added): YAML validated by Pydantic into a frozen object
  with a content hash. An unknown failpoint name fails at load, before any process starts (**done**).
- Batch, cell, and trial ids on every event. Each trial's seed is `sha256(master seed, cell, trial)`, recorded even
  though nothing randomizes yet. Each batch directory gets the manifest from the `doctor` code, plus the scenario's
  content hash and the clause-registry version, and the batch record from `schemas/v1` with `provenance: "run"` and
  the manifest's sha256 (**done**).
- Open each trial on the effect sink with its batch, cell, and trial ids. Before each batch, read the sink's
  `/health` and refuse to run if its test hooks are enabled or its source hash doesn't match the batch manifest
  (**done**; also reread after every trial).
- Workers reach Postgres through the Toxiproxy route with no toxics installed, so adding network faults later doesn't
  change the topology. Each worker gets its own proxy and port, because a toxic applies to every connection through
  its proxy and a fault must be able to target one worker. Worker pools use the saver's documented defaults
  (`autocommit=True`, `prepare_threshold=0`, `dict_row`) (**done**).
- Linux only: `crashcourt run` refuses to start on a host without POSIX signals and says to use WSL2, and the README
  quickstart covers running it under WSL2 on Windows (**done**).
- A trivial two-node smoke graph with no effects, and `scenarios/smoke.yaml` (**done**).
- `crashcourt run <scenario> --trials N`, which writes every process's history and the merged history into the
  trial's directory (**done**).
