## Decisions
1. **Hash chain.** Each row stores `prev_hash` and `row_hash = sha256(prev_hash | JSON of its fields)`, starting from a
   zero genesis. Verification recomputes the chain and reports the first bad `sink_seq`. A chain cannot detect the
   *last* rows being removed. The workers' `effect.response` events record each `sink_seq` they were given, which is
   the external check.
2. **One ledger file per trial.**
   - `POST /trials` opens `<data>/<batch>/<cell>/trial-NNNNN.sqlite`; the file refuses a different trial, and its meta
     rows are read and written in one transaction.
   - The open trial is persisted (`current.json`, written atomically, directory fsynced on POSIX), so a restarted
     sink resumes it. A trial it cannot resume (a file from another ledger version) leaves the sink up with no
     trial open; `/health` says why and doctor fails until a trial is opened.
   - `POST /trials` opens the new file before closing the old one. A file that belongs to another trial (the seed
     is not in the path) or another ledger version gets 409, and the open trial keeps working.
   - Per-trial files are self-contained evidence, and the ledger rows become the sink's history (`ledger_events`)
     rather than a second record written in parallel. events.py now says so: each row commits before the sink
     answers, which is what the merge's append-to-response edge relies on.
3. **Requests are bound to their trial and their worker.** `POST /effects`, `POST /attempts/next`, `GET /ledger`,
   and `GET /ledger/verify` name their trial and get 409 unless it is the open one, so a late request from a
   previous trial's worker cannot land in the next trial's ledger, and a reader cannot take one trial's rows for
   another's; the client also checks the trial in each answer. `record_effect` takes the trial from its history writer and refuses an effect whose worker or pid
   differs from the writer's, because the merge links the sink's append to the worker by that name. logical_op, pid,
   thread_id, and node are required; only the checkpoint the worker saw may be unknown.
4. **Durability and versions.** WAL (checked: SQLite answers with the mode it is in) with `synchronous=FULL`; each
   append and counter increment is its own committed transaction before the HTTP answer. Requiring the row fields
   changed the schema, so the ledger is version 2; a version-1 file is refused rather than reopened with nullable
   columns.
5. **A test hook in the oracle, fenced.** `CRASHCOURT_SINK_TEST_EXIT_AFTER_COMMIT` exits the process right after a
   commit. It is the only way to prove "commit before response" on a real process. It is off by default, `/health`
   reports it, and doctor fails if it is armed.
6. **Attempt counters** are keyed `model/<thread>/<node>/<turn>` and stored in the trial's ledger file. A replacement
   worker gets the next attempt.
7. **The scripted model is a plain class returning `AIMessage`, not a LangChain chat model.** It keeps the key
   explicit (thread, node, turn, attempt) instead of recovering it from callback metadata. The message id carries the
   same key, so a re-run adds a distinguishable message. T-09's workloads call it.
8. **Clock.** The ledger stamps `received_mono_ns` with the same monotonic clock function as the history writer
   (T-04), whose helper is now public. The merge breaks ties with `mono_ns`, so the sink's stamps compare with the
   workers' only when they share a kernel: on Linux, where batches run (T-07's runner refuses other hosts). On this
   Windows host the sink runs in Docker Desktop's VM, and doctor measured its clock 830.7 s behind the host's.
   `/health` reports the sink's clock, and doctor shows the offset, so a batch can check it.
9. **Errors the worker sees.** A sink that refuses a request (4xx) did not apply the effect, so `effect.response` is
   `fail`. No answer, a cut-off body, or a body that is not JSON leaves the outcome unknown: `info`, as a
   `SinkError`.
10. **Which sink is running.** compose rebuilds the sink on every `up` (`pull_policy: build`), so an image from
   another checkout is not reused. `/health` reports a sha256 over the crashcourt package's Python source and the
   build inputs (pyproject.toml, uv.lock, .python-version, Dockerfile.harness), and doctor compares it with the
   checkout's. The image copies .python-version, so uv installs the pinned 3.12.13; without it, uv (allowed only its
   own Pythons) had installed 3.13.
   The manifest records no sink hash: its schema is v1 and frozen, and a manifest is written only after doctor passes,
   so its `git_sha` names the source the sink was checked against.
11. **Doctor, not the manifest, for the image.** The sink is built, not pulled, so the manifest's image list is
    unchanged. Doctor checks the sink's health, ledger version, source, and test hook, and that every `FROM` in
    `Dockerfile.harness` is pinned.
12. **New C7 reference.** FastAPI and uvicorn changed uv.lock. research/evidence/t-08/manifest-local.json, recorded at
    1c2e7f9, differs from T-02's pinned fields only in `lockfile_sha256`. On top of T-04, uv would have locked FastAPI 0.143.0, which
    adds opentelemetry-api; the lock keeps 0.141.1, the version this task was built and reviewed with.

## Review fixes
The review of 751e5eb (2026-10-08) asked for three changes and five smaller ones:

1. **A stale sink passed doctor.** compose rebuilds the sink, `/health` reports a source hash, and doctor checks it
   (decision 10). Locally, a docstring change made doctor fail until the sink was rebuilt.
2. **Effects were not tied to their trial.** Requests name their trial and get 409 on a mismatch (decision 3).
3. **`record_effect` trusted `effect.worker`.** It now refuses an effect whose worker or pid differs from the history
   writer's (decision 3).

Smaller: logical_op, pid, thread_id, and node are required, and the dump is regenerated with them; the meta insert
and the `current.json` write are atomic; the WAL mode is checked; the merge test puts the sink's clock before the
request or after the response, so it fails without the causal edges; the record's counts and CI run are current.

Also changed on top of T-04: the sink's ok responses already carried `sink_seq`, as T-04's merge now requires; the
docstrings drop section references to a document outside the repository.

A second review of those fixes found more, fixed here:
- The sink's clock is not the host's on Windows (decision 8).
- A refused `POST /trials` closed the open ledger and left every request failing; reads were not tied to a trial
  (decisions 2 and 3).
- The source hash ignored uv.lock and the other build inputs, and the image ran Python 3.13 (decision 10).
- A version-1 ledger file reopened silently (decision 4).
- Some client failures escaped without an `effect.response`, and refusals were recorded as unknown (decision 9).
- Smaller: the endpoint table, the merge's wording about the sink, the directory fsync, the state lock around reads
  of the open ledger, and the model's note on binding the trial to the attempt counter.
