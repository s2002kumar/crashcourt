# T-06 evidence: control C4 for the failpoint wrapper

Generated by `c4.py` (needs the compose services): `uv run python research/evidence/t-06/c4.py`.

## Conformance: identical through the wrapper

`conformance.md` runs langgraph-checkpoint-conformance 0.0.2 on InMemorySaver, AsyncSqliteSaver, and AsyncPostgresSaver,
raw and wrapped. The three reports are identical: every saver is FULL, with 58 of 58 base tests passing, and no
extended capability is detected. The same comparisons run as tests (tests/unit/test_failpoint_transparency.py,
tests/integration/test_failpoint_postgres.py).

## Overhead: the wrapper is negligible; recording events is not

`overhead-linux.md` measures p50 and p99 of `put` on Linux (the harness platform: a Linux container on the compose
network, reaching Postgres at postgres:5432). Three variants run interleaved in a rotating order.

| `put` on Postgres, p50 | Sync | Async |
| --- | --- | --- |
| Wrapped, no history | -0.7% | +0.3% |
| Wrapped, with history | +12.7% | +11.1% |

C4 asks for an investigation above 5%. The findings, from diagnostics run in the same container:

1. **The database call is unchanged.** Inside the wrapper, the inner `put` took 1,803 µs at p50 against 1,785 µs for
   the raw saver. All of the added time is the two history events recorded before and after it: about 163 µs per
   `put`.
2. **Garbage collection is not the cause.** Disabling it changed nothing.
3. **Most of the cost is CPU work on cold caches.** Right after a `put` returns, building one event costs about 57 µs
   of Pydantic validation, 27 µs of JSON serialization, and 11 µs (tmpfs) to 23 µs (overlay filesystem) of `write`. In
   a warm loop the same event costs about 25 µs in total.

What this means for results:

- **Deterministic cells are unaffected.** The overhead is a constant delay before and after each saver call, never
  inside the database interaction, and those cells order events with barriers, not timing.
- **Randomized cells shift slightly.** Their timing distributions move by about 0.2 ms per saver call, and the
  manifest and methodology must say so.
- **A cheaper emit is possible.** Validating events once per kind, or serializing without full validation for events
  the writer itself builds, would cut the cost. I have proposed this as a follow-up rather than changing the frozen
  writer in this task.

The Windows host was too noisy to measure on: two runs gave a raw Postgres `put` p50 of 3.3 ms and 11.1 ms, so no
Windows numbers are recorded.
